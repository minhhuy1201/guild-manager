# Frontend structure and conventions

Why `apps/web` is laid out the way it is, the rules that keep it that way, and the display
conventions every screen follows. This is the only doc under `apps/web/docs/`.

The binding description of what exists today — stack, `app/` vs `features/`, the session model —
is [`docs/architecture.md`](../../../docs/architecture.md) §4. When the two disagree, architecture.md
wins and this file needs fixing.

Running the app, env vars, commands: [`README.md`](../README.md).
The backend counterpart of this document: [`apps/api/docs/backend.md`](../../api/docs/backend.md).

---

## 1. The idea

`app/` is Next.js's routing surface, not a place to put code. Everything that *is* the product lives
in `features/<feature>/`, one folder per domain, each with the same internal shape and a single
public entry point. Same principle as the backend: **things that change together stay together**,
and a folder listing should tell you what the app does.

There are five features — `attendance`, `auth`, `members`, `settings`, `team-builder` — and they map
one-to-one onto what a user can do.

## 2. Overall layout

```
apps/web/
├── app/                            # routing and layout ONLY — one thin page per route
│   ├── layout.tsx                  # <Providers> + app shell
│   ├── page.tsx                    # / — attendance
│   ├── lich-su-diem-danh/page.tsx  # attendance history
│   ├── xep-team/page.tsx           # team builder (admin)
│   ├── thiet-lap/page.tsx          # settings (admin)
│   └── globals.css                 # Tailwind 4 + theme variables
│
├── proxy.ts                        # ⭐ session refresh + admin route guard, before every page request
│
├── features/                       # ⭐ all the logic
│   └── <feature>/
│       ├── api/                    # request functions (through apiFetch) + query key factory
│       ├── hooks/                  # TanStack Query hooks
│       ├── store/                  # Zustand — UI state only
│       ├── lib/                    # pure feature logic (derivations, labels, diffing)
│       ├── types/                  # feature-internal types
│       ├── components/
│       ├── __tests__/              # beside the folder they cover (Vitest)
│       └── index.ts                # the feature's ONLY public surface
│
├── components/
│   ├── ui/                         # generated by the shadcn CLI — never hand-edited
│   ├── shared/                     # cross-feature wrappers and the app shell
│   └── providers.tsx               # QueryClientProvider + TooltipProvider
│
├── hooks/                          # cross-feature hooks (use-table-pagination)
├── config/                         # routes.ts (ROUTES), api.ts (API_BASE_URL)
├── lib/                            # api-client.ts, format.ts, guild-class.ts, utils.ts
├── components.json                 # shadcn config (style: base-nova, lucide icons)
├── vitest.config.ts
└── tsconfig.json
```

Stack: Next.js 16 App Router (React 19) · Tailwind CSS 4 + shadcn/ui on `@base-ui/react` ·
TanStack Query for server state · Zustand for UI state · dnd-kit on the team builder · Vitest.

All user-facing copy is **Vietnamese**. Identifiers and file names are English.

## 3. Inside one feature

Every feature has the same shape, so "where is this?" always has the same answer:

```
features/members/
├── api/
│   ├── members-api.ts              # "use server" — the calls that need the admin token
│   └── members-keys.ts             # query key factory
├── components/
│   ├── members-panel.tsx
│   ├── member-row.tsx
│   ├── member-form-dialog.tsx
│   └── delete-member-dialog.tsx
├── hooks/
│   ├── use-members.ts              # useQuery
│   └── use-member-mutations.ts     # useMutation + invalidation
└── index.ts                        # everything another module may import
```

`store/` and `lib/` appear only when the feature needs them — `members` has neither, `team-builder`
has both (a formation store, a pool filter store, and a dozen pure `lib/` modules with their own
tests). **Don't create empty folders to match the template.**

A query key factory lives in its own file (`*-keys.ts`) whenever the API file is `"use server"`: a
`"use server"` module may only export async functions, so a plain `const` object cannot live there.

## 4. Data-flow rules

These are the rules that get broken first, in the order they get broken:

1. **`app/` is routing and composition only.** A page renders one feature component and nothing else.
   Logic never lives in `app/`.
2. **Server data → TanStack Query**, in `features/<feature>/hooks/`. **Never** put an API response
   into Zustand.
3. **UI state → Zustand**, in `features/<feature>/store/` — filters, dialogs, drag state. Nothing
   that came from the network.
4. **`lib/api-client.ts` is the only place that calls `fetch` against the backend.** Feature request
   functions wrap `apiFetch` in `features/<feature>/api/`. Components never fetch and never call
   `useQuery` directly — they call the feature's hook.
5. **Never import another feature's internal file.** Go through its `index.ts`.
6. **Prefer Server Components.** `"use client"` only where interactivity actually requires it.
7. **Import with `@/`.** Route paths come from `config/routes.ts` (`ROUTES`), never string literals.

Shared code from the workspace package is imported as `@shared/*` (→ `packages/shared`). These
aliases exist in `apps/web` only — `apps/api` has none, it imports relatively and uses the real
package name `@guild/shared/*` (see [`architecture.md`](../../../docs/architecture.md) §3.2). Both
web aliases are declared twice, in `tsconfig.json` and in `vitest.config.ts`; a new alias must be
added in both or tests fail on imports that type-check fine.

### The API boundary

`apiFetch` does three things so no one else has to: it prefixes `API_BASE_URL`, unwraps the
backend's `{ data }` envelope (with `204` returning `undefined`), and turns any error status into an
`ApiError` carrying the backend's **Vietnamese** message.

**Render that message as-is.** The backend writes error text meant for the user; re-wording it in
the UI just creates two vocabularies for the same failure.

### Server actions and the admin token

The session lives in **httpOnly cookies**, so client JavaScript cannot read the access token and
cannot set an `Authorization` header. Any call that needs admin rights therefore runs on the server:
a `"use server"` module in `features/<feature>/api/` reads the token (`getAccessToken` from
`features/auth`) and calls `apiFetch` with the header attached — `members-api.ts`,
`mark-attendance-action.ts`, and the settings/team-builder equivalents all follow this shape.

Each of those files repeats a tiny local `authHeader()` helper. That duplication is deliberate and
documented in the code: a `"use server"` file may only export async functions, so the helper cannot
be shared from one.

### The session

The API signs an access token (1 day) and a refresh token (1 week); both are stored in httpOnly
cookies. `proxy.ts` runs before every page request and does two things:

- **Renews the pair** when the access token has expired but the refresh token has not. The proxy is
  the only place in Next.js that can write cookies for an arbitrary request, which is why refresh
  cannot live in a Server Component. It writes the new tokens onto both the request (so this
  render sees them) and the response (so the browser keeps them).
- **Redirects anonymous visitors away from admin routes** — the prefixes in `ADMIN_PATH_PREFIXES`
  (`/xep-team`, `/thiet-lap`).

Hiding a nav link is cosmetic. Real enforcement is the proxy, plus a `getSession()` check inside each
admin page's server component, plus the guards on the API. A new admin route needs all three.

### Time and deadlines

The week boundaries, the Saturday 22:00 rollover and every deadline rule are **the backend's
business** (`apps/api/src/modules/battle-sessions/session-schedule.ts`, summarised in
[`architecture.md`](../../../docs/architecture.md) §6). The frontend only mirrors the
`isDeadlinePassed` flag the API sends, to grey out a locked column, and re-checks it on a timer
(`use-deadline-refresh`) so a column locks without a reload.

**Never re-derive a schedule rule on the client.** Two implementations of one rule drift, and the
one the user sees would be the wrong one.

The one rule the settings form does evaluate locally — the deadline cap in `session-form-dialog` —
is not a second implementation: it calls `deadlineCapFor` from `@shared/lib`, the same
function the API validates with. The server still decides; the local call only prefills the field and
shows the error before a round-trip.

## 5. Components

Three layers, with a strict rule between them:

| Folder | What it is | Rule |
|---|---|---|
| `components/ui/` | Stock shadcn components | **Generated output — never hand-edited.** Add with `pnpm dlx shadcn@latest add <component>` |
| `components/shared/` | Cross-feature wrappers and the app shell | Where a variant or a convention lives |
| `features/*/components/` | Screens and their parts | Feature-owned, not importable from elsewhere |

Everything in `components/ui/` comes from the shadcn CLI in its **Base UI flavour**
(`components.json` → `style: "base-nova"`, `iconLibrary: "lucide"`) — no Radix, no hand-written
primitives. Need a variant? **Wrap it in `components/shared/`** instead of editing the generated
file, the way `status-badge.tsx` composes the stock `Badge` with semantic tones. That way
regenerating a component never eats a local change.

Current shared building blocks: `action-buttons`, `date-range`, `error-state`,
`guild-class-filter-select`, `guild-class-icon`, `main-nav`, `page-size-select`, `password-input`,
`site-header`, `status-badge`, `status-icon`, `table-pagination`, `table-pagination-bar`,
`table-skeleton`.

## 6. Display conventions

System-wide, so screens look like one app. **Extend this section when you add a convention.**

### Binary state → an icon, never words

Any column or card showing a **Có/Không, Đạt/Không, Bật/Tắt** style state uses a coloured round
icon, not text:

- **success** → green tick (`Check`, emerald background)
- **danger** → red cross (`X`, destructive background)

Use **`components/shared/status-icon.tsx`** (`<StatusIcon tone label />`). `label` is required — the
icon has no visible text, so it is the only thing a screen reader gets.

In use on the attendance grid (`attendance-row`, both read-only and toggling) and the attendance
history table (`attendance-log-table`).

> Not to be confused with `status-badge.tsx`: a badge **has words** and is for descriptive labels
> ("Đã khóa" / "Đang mở" on the week timeline), not for binary state.

### Guild class → an icon with a tooltip

Class names are long and every table is narrow, so a character's class always renders as
`components/shared/guild-class-icon.tsx`: an avatar image with the class name in a tooltip and in
the image `alt`.

The images live in `public/img/` and are mapped in `lib/guild-class.ts` — they are a web asset, so
the mapping stays on the frontend while the enum itself comes from `@shared/enums`:

| Class | Image |
|---|---|
| Cửu Linh | `/img/cuuLinh.png` |
| Huyết Hà | `/img/huyetHa.png` |
| Long Ngâm | `/img/longNgam.png` |
| Thần Tương | `/img/thanTuong.png` |
| Thiết Y | `/img/thietY.png` |
| Toái Mộng | `/img/toaiMong.png` |
| Tố Vấn | `/img/toVan.png` |

### Actions

From `components/shared/action-buttons.tsx`:

- **Create** → a button *with* a label (`CreateButton`), at the start or end of the list.
- **Edit / delete on a row** → icon buttons (`EditAction`, `DeleteAction`) inside `RowActions`,
  always with a tooltip *and* `sr-only` text, so the action is discoverable by mouse and readable by
  a screen reader.
- **Destructive actions get a confirm dialog** — see `delete-member-dialog`, `delete-session-dialog`,
  `delete-match-dialog`.

### Tables

- Loading → `table-skeleton` inside `<TableBody>`, with the same column count as the header.
- Failure → `error-state` in place of the content, showing `ApiError.message` and a retry button.
- Paging → `use-table-pagination` (client-side, resets to page 1 when the filter changes) rendered
  with `table-pagination-bar` / `page-size-select`.

## 7. Naming conventions

| Kind | Convention | Example |
|---|---|---|
| Folder | `kebab-case` | `features/team-builder/`, `components/shared/` |
| File | `kebab-case.tsx` / `.ts` | `attendance-row.tsx`, `session-subtitle.ts` |
| Component | `PascalCase`, matching the file name | `AttendanceRow`, `StatusIcon` |
| Hook | `camelCase` with a `use` prefix | `useAttendanceBoard` |
| Type / interface | `PascalCase`, **no** `I` prefix | `SessionUser`, `StatusIconProps` |
| Constant | `SCREAMING_SNAKE_CASE` | `ROUTES`, `API_BASE_URL`, `ACCESS_TOKEN_COOKIE` |
| Boolean | `is` / `has` / `should` / `can` prefix | `isDeadlinePassed` |
| Query key factory | `<feature>Keys` in `<feature>-keys.ts` | `memberKeys`, `attendanceKeys` |
| Barrel `index.ts` | one per feature, nothing else | |

Route paths are Vietnamese because they are user-visible (`/xep-team`, `/thiet-lap`); they are
declared once in `config/routes.ts` and referenced as `ROUTES.*`.

## 8. Tests

Vitest, `pnpm test`. Tests live in `__tests__/` beside the folder they cover and run in the **node**
environment by default. There are no component tests; there are hook tests, and those need a DOM —
a hook test file opts in with `// @vitest-environment jsdom` on its first line, so the rest of the
suite stays on node. `vitest.config.ts` pins `TZ=Asia/Ho_Chi_Minh`, because half the logic under
test is about Vietnamese-time boundaries and it must not depend on the machine running it.

What is worth testing here is the pure `lib/` layer — `assignment`, `formation-diff`, `prefill`,
`pool`, `session-status`, `date-parts`, `session-subtitle` — plus `lib/api-client.ts`. Extracting
a derivation into `lib/` so it can be tested without rendering is the intended move.

Above that layer sit the hooks that wire it together, where the real bugs live: the five hooks of
`features/team-builder` are covered in `features/team-builder/hooks/__tests__/`, rendered with
`@testing-library/react` through the shared `renderFormationHook` helper (fresh QueryClient, both
Zustand stores reset).

## 9. Anti-patterns

| ❌ Wrong | ✅ Right |
|---|---|
| `fetch` inside a component or a hook | The feature's `api/` function, over `apiFetch` |
| API data in a Zustand store | TanStack Query owns server state; Zustand owns UI state |
| Logic in `app/<route>/page.tsx` | A thin page rendering one feature component |
| `import { X } from "@/features/other/lib/x"` | Import from the feature's `index.ts` |
| Editing `components/ui/button.tsx` | Wrap it in `components/shared/` |
| Re-writing the backend's error message | Render `ApiError.message` verbatim |
| Recomputing a deadline on the client | Use the `isDeadlinePassed` the API sent |
| Hardcoding `"/thiet-lap"` | `ROUTES.settings` |
| `"use client"` at the top of every file | Server Component by default; opt in where needed |
| An admin route guarded only by hiding its nav link | `ADMIN_PATH_PREFIXES` + `getSession()` in the page + the API guard |

---

## 10. Summary

Three questions to check the structure with:

1. Adding a screen → one thin page in `app/`, everything else inside one `features/` folder?
2. Deleting a feature → does one folder plus one route go away cleanly?
3. Looking at `features/` → can you tell what the app does?
